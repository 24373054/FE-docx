# 工作分解结构与证据型完成定义

## 1. 文件目的

把项目拆分为可分派、可验收、可阻断的工作包。

“文档已写”“会议已开”或“采购已到货”不构成工作包完成，必须有直接结果、独立复核和阶段门证据。

## 2. 当前状态

项目处于G0/V0：

- 工作包责任人未具名任命；
- 公司预算未批准；
- 主管机关问题未授权提交；
- 用户访谈未开始；
- 产品和系统未实现；
- 方法、工具、样本和人员批准数均为0；
- 质量体系未运行；
- 真实试点和申报未开始。

本WBS是签批输入，不是执行授权。

## 3. 分解规则

每个工作包必须包含：

- work package ID；
- 目标和非目标；
- 前置依赖；
- 输入及其版本；
- 任务和子交付；
- 责任/复核/批准角色；
- 完成定义；
- 证据ID；
- 风险、停止和重开条件；
- 预算和时间上限；
- 当前状态。

## 5. 工作流关系

```text
治理
 ├─ 监管 ──> 产品范围 ──> 方法/数据 ──> 工具/架构
 ├─ 人员 ───────────────────────┤
 └─ 质量 ───────────────────────┤
                                  ├─> 模拟验证
监管 + 人员 + 质量 + 方法 + 工具 ──> 实验室/申请
用户 + 合规 + 验证 ───────────────> 受限试点
全部前置 ────────────────────────> 发布/交付
```

依赖未满足时不得通过“并行推进”绕过。

## 6. G0工作包

当前允许：

- 完成治理签批材料；
- 维护权威来源和问题包；
- 设计用户访谈；
- 公开/合成数据样本研究；
- 重构文档和目录；
- 形成可取消资源方案。

G0禁止：

- 对外代表公司行动（未授权时）；
- 接收真实案件材料；
- 宣称产品/方法已支持；
- 不可逆采购；
- 启动申报；
- 生产发布。

## 7. 技术验证工作包

每个技术包内部按相同子结构：

1. 问题与范围；
2. 官方协议/标准；
3. 对象与数据源；
4. 样本与真值；
5. 方法候选；
6. 工具/环境；
7. 正常和负向执行；
8. 独立复核；
9. 差异与缺陷；
10. 确认报告；
11. 变更和能力保持。

不同链不得仅复制同一结论。

## 8. 完成定义

工作包只能标记`completed`，当：

- 交付范围与版本冻结；
- 所有前置依赖有证据；
- 责任人实际执行；
- 测试/审查有实际输出；
- P0/P1关闭；
- 独立复核完成；
- 批准人具名签批；
- 残余风险和后续触发明确；
- 索引、追踪和状态同步。

否则使用`planned`、`in_progress`、`blocked`或`verification`。

## 10. 变更控制

新增/拆分/取消工作包时记录：

- 变更理由；
- 影响目标和非目标；
- 依赖、资源和时间；
- 法规、数据和安全影响；
- 已形成交付和历史任务；
- 新完成定义；
- 回退/停止；
- 批准。

紧急变化不免除事后记录和复核。

## 11. 进度报告

每个工作包报告：

- 状态和证据ID；
- 本期实际完成；
- 未满足完成定义；
- P0/P1及阻断天数；
- 依赖和责任人；
- 预算实际/承诺；
- 下期可验证输出；
- 需要管理层决定。

不使用无分母“完成百分比”。
