# 文件与记录控制程序

## 1. 文件目的

规定文件从创建、评审、批准、发布、修订到撤回的生命周期，以及记录从产生、唯一标识、修订、保护、检索、保留、暂停销毁到处置的最低控制。

本程序防止把Git提交、哈希、自动检查、电子签名外观或模板填写误写为公司批准、事实发生或记录不可否认。

## 2. 适用范围与边界

### 2.1 纳入

- 00至10目录的受控Markdown文档及其索引；
- requirements、controls、tests和traceability目录；
- 方法、工具、样本、真值、人员、设备和供应商记录；
- 未来任务/案件的原始记录、派生对象、复核、报告和交付记录；
- 外来法规、标准、主管机关答复、供应商说明和合同附件；
- 纸质、电子、数据库、日志、音视频和签名记录。

### 2.2 排除和限制

- 本程序不自行确定所有记录的法定保留年限；
- Git不是批准系统，提交者不自动成为批准人；
- SHA-256证明特定字节一致，不证明内容真实、完整或法律有效；
- 当前无公司受控文档平台、电子签名平台或真实案件档案库；
- 公开验证包不得包含公司人员隐私、真实案件、个人信息、私钥或令牌。

## 3. 文件、模板与记录的区别

|对象|定义|例子|可否证明活动发生|
|---|---|---|---|
|文件|规定要求、方法或计划|QMS、SOP、METHOD|否|
|模板|预定义字段的空白或候选结构|FRM-001至016|否|
|记录|活动发生时形成且受保护的证据|批准、运行、复核、日志|在真实性与完整性满足时可以|
|目录|需求、控制、测试及映射状态|catalogs/*.csv|只证明登记状态|
|证据包|有manifest和对象关系的记录集合|validation-evidence|只证明包内对象，不自动证明结论|

研究会话填写的模板实例必须标记为模拟、未批准或未发生事项，不能替代公司自然人的运行记录。

## 4. 状态与职责

### 4.1 文件状态

允许状态由治理基线定义。典型流转：

```text
历史生成稿 → 受控草案/研究底稿 → 待批准 → 已批准 → 已生效
                                             ↘ 暂停/已废止
```

“已批准”要求具名批准、日期、范围和批准证据；“已生效”还要求发布、培训、依赖和权限就绪。

### 4.2 职责

|角色|职责|禁止|
|---|---|---|
|作者|编制、来源、变更说明、自检|自我完成全部技术与质量批准|
|技术复核人|核对专业内容、范围和可执行性|复制作者结论|
|质量负责人|状态、结构、记录、依赖和发布审查|用格式通过替代技术结论|
|批准人|决定批准、条件、退回或废止|批准超出本人权限的文件|
|配置管理员|唯一ID、版本、索引、发布和撤回|自行更改批准内容|
|记录责任人|及时创建、保护、检索和移交|覆盖原始记录|
|安全/数据负责人|权限、备份、暂停销毁和处置|无审批访问内容|

## 5. 详细控制要求

### QMS-002-C001｜文件创建

- 新文件应先确认主题、层级、唯一document_id、责任人、适用范围和现行文件冲突。
- 内容应区分事实、要求、假设、示例和未发生状态。
- 无责任人、目的或替代关系的文件不得进入受控评审。

### QMS-002-C002｜技术复核

- 技术复核人应核对专业准确性、适用前提、计算/流程可复现性和限制。
- 复核应记录问题、证据、处理决定和未解决保留意见。
- 参与主要编制者不得作为唯一技术复核人。

### QMS-002-C003｜质量审查

- 质量审查应核对状态、元数据、结构、术语、依赖、记录要求、停止门和目录一致性。
- 自动检查结果只能作为质量审查输入。
- 技术、法律或方法问题不得用“格式通过”关闭。

### QMS-002-C004｜批准生效

- 批准必须记录批准人身份、权限、决定、范围、条件、日期和可验证证据ID。
- 生效还应确认现行版本发布、旧版撤回、培训、工具/权限和依赖就绪。
- 空白签批、作者自批、AI生成或Git合并不得解释为批准。

### QMS-002-C005｜受控发布

- 配置管理员只能发布与批准对象字节、版本和状态一致的文件。
- 发布清单应包含路径、document_id、版本、状态、批准证据、替代文件和生效时间。
- 公开、内部和敏感版本应分发到相应权限域。

### QMS-002-C006｜版本标识

- 每个受控文件应有可读版本，并与变更范围和成熟度相符。
- 文档版本、Git提交和证据对象哈希是不同标识，不得互相替代。
- 仅修正索引或格式时也应能够追踪所影响的内容基线。

### QMS-002-C007｜旧版撤回

- 新版生效时应从工作入口撤回旧版并保留历史审计副本。
- 旧版必须标明已替代/废止、替代版本、日期和适用历史范围。
- 无法确认现场副本是否撤回时，不得宣称发布完成。

### QMS-002-C008｜外来文件

- 法规、标准、答复、合同、供应商说明和数据源文档应登记来源、版本/日期、适用范围、访问位置和责任人。
- 摘要不得替代原件；版权或权限限制应记录。
- 外来文件失效、撤回或访问中断时应评估既有方法与结果。

### QMS-002-C009｜查新

- 外来法律、监管、标准和关键供应商资料应按风险设置查新频率和触发事件。
- 查新记录应同时保留“有变化”和“无变化”的检索范围、日期与人员。
- 搜索引擎结果或非权威转载不能单独关闭高风险问题。

### QMS-002-C010｜记录唯一编号

- 每条关键记录应有全局或所属任务内唯一ID，并可解析其对象类型与父关系。
- 重新导出、修订或派生记录不得复用原对象ID。
- 编号冲突或父关系不明时应隔离对象并修复映射。

### QMS-002-C011｜原始记录

- 原始记录应在活动发生时形成，保存原始格式、时间、来源、操作者和环境。
- 对系统自动日志应验证日志开启、时间和防篡改/完整性机制。
- 转录、截图或摘要不得静默替代原始对象。

### QMS-002-C012｜修订追加

- 已形成记录的修正应保留原值、新值、原因、人员、时间和复核。
- 不允许覆盖原始记录或回填未发生的批准。
- 影响结论的修订应触发复核、历史影响和必要的报告更正。

### QMS-002-C013｜电子签名

- 电子签名方案应验证签名人身份、意图、权限、签名对象、时间、完整性和验证方式。
- 扫描签名图片、姓名文本或账号登录不能自动满足可信签署要求。
- 签名证书、平台或验证链失效时应保留可验证的长期证据或迁移记录。

### QMS-002-C014｜时间同步

- 关键系统、节点、工作站、日志和签名平台应登记时间源、时区、同步状态和允许偏差。
- UTC、北京时间、区块时间和系统本地时间应明确区分。
- 时间异常可能改变顺序或授权判断时，应停止并评估影响。

### QMS-002-C015｜附件哈希

- 关键附件和证据对象应记录算法、哈希值、字节数、计算时间和对象身份。
- 哈希清单和manifest应引用相同对象字节与规范化规则。
- 哈希一致不等于来源可信或内容正确；仍需来源、权限和语义复核。

### QMS-002-C016｜访问控制

- 文件与记录权限应按角色、数据密级、任务、期限和最小必要性授予。
- 创建、修改、批准、发布、删除和审计权限应尽量分离并记录。
- 离职、调岗、冲突、事件或授权到期时应撤销并验证。

### QMS-002-C017｜留存期限

- 应建立记录类别级保留表，列明法律/合同依据、起算点、期限、责任人和处置。
- 不同主体路线、任务与数据类别不得无依据采用同一固定年限。
- 保留到期前应检查诉讼、调查、投诉、CAPA和法律暂停。

### QMS-002-C018｜备份恢复

- 备份应定义范围、频率、加密、隔离、副本、责任人和恢复目标。
- 只有完成从受控空环境恢复并核验对象完整性，才能证明恢复能力。
- 备份成功日志不能替代定期恢复演练。

### QMS-002-C019｜合法暂停销毁

- 涉及诉讼、调查、投诉、不符合、安全事件或主管机关要求时应暂停计划销毁。
- 暂停应记录范围、依据、开始、责任人、访问限制和解除条件。
- 解除暂停须由有权人员批准，不能由存储管理员单独决定。

### QMS-002-C020｜销毁证明

- 销毁前应确认批准、对象清单、到期依据、备份/副本、暂停状态和方法。
- 销毁证明应记录对象ID、数量、介质、方式、人员、见证/系统证据、时间和异常。
- 无法证明所有副本已处理时，应记录残余位置与风险，不得写成完全销毁。

## 6. 标准工作流程

### 6.1 文件

1. 作者创建变更请求和文件草案；
2. 配置管理员检查ID、路径和现行冲突；
3. 技术复核人记录问题与结论；
4. 质量负责人完成质量审查；
5. 具名批准人作出批准、条件批准、退回或废止决定；
6. 配置管理员生成发布清单、撤回旧版并分发；
7. 文件责任人完成培训/告知和生效确认；
8. 变更或到期时重新进入流程。

### 6.2 记录

1. 活动发生时创建唯一记录；
2. 绑定人员、时间、来源、对象和任务；
3. 保存原始记录及必要哈希；
4. 复核完整性和差异；
5. 按密级存储、授权和备份；
6. 到期前检查暂停销毁；
7. 经批准销毁并形成证明，或继续保留并记录理由。

## 7. 最低元数据与状态登记

### 7.1 文件

至少包含document_id、标题、版本、状态、类型、责任人、批准人、生效日期、复审周期、密级、替代关系和批准证据。

### 7.2 记录

至少包含record_id、对象类型、任务/项目、创建人、创建时间、来源、父对象、版本/修订、密级、保留类别、访问、完整性和处置状态。

### 7.3 目录状态

目录状态只按实际证据升级：

- requirement：`generated_unreviewed → reviewed → approved/rejected`；
- control：`not_implemented → implemented → verified/retired`；
- test：`not_executed → passed/failed/blocked`。

文件重构可以支持需求`reviewed`，不能自动把控制写为`implemented`或测试写为`passed`。

## 8. 主要风险与控制

|风险|控制|停止条件|
|---|---|---|
|提交即批准|签批证据和状态分离|批准字段为空|
|记录覆盖|追加修订和原始对象保护|前值无法恢复|
|外来文件过期|查新与影响评估|关键依据状态不明|
|时间顺序不可信|同步记录、时区和异常门|偏差影响结论|
|哈希过度解释|来源、语义和权限复核|只有哈希无来源|
|备份不可恢复|空环境恢复演练|未验证恢复|
|销毁违规|保留表和法律暂停|暂停状态不明|
|公开泄密|密级、扫描和最小权限|发现敏感对象|

## 9. 保留与处置决策

保留表在公司主体、法律路线和合同模板确认后建立。当前仅执行保守原则：

- 公开研究包按版本保留；
- 治理签批、授权、验证、审计和不符合记录不得因文件改版删除；
- 真实案件/客户记录未获接收授权，故当前不应存在；
- 发现误入公开仓库的敏感数据时，先隔离、事件响应和证据保存，再决定历史清理；
- Git历史清理属于高风险处置，须由安全、质量、法律和仓库所有者共同批准。

## 10. 验收准则

- [ ] 文件与记录定义、状态和责任边界清楚；
- [ ] 技术复核、质量审查、批准和发布至少实现必要分离；
- [ ] 唯一ID、版本、替代与索引无冲突；
- [ ] 外来文件查新和影响评估有实际记录；
- [ ] 原始记录不可覆盖，修订可追溯；
- [ ] 签名、时间和哈希的能力与限制经过验证；
- [ ] 访问、离职撤权、备份和恢复完成演练；
- [ ] 保留表及法律暂停流程获批准；
- [ ] 至少模拟一次销毁并验证证明字段；
- [ ] 20项控制保持与实际实施状态一致。

## 11. 当前结论

程序已从乱码生成稿重构为受控草案。现有Git和公开证据包可支持版本与完整性研究，但没有公司批准系统、电子签名验证、正式保留表或真实案件档案运行证据。

## 12. 审核证据与抽样策略

### 12.1 审核证据

- 现行文件清单、批准证据和分发/培训记录；
- 变更请求、技术复核、质量审查和旧版撤回；
- 外来文件登记、查新和影响评估；
- 原始记录、修订历史、签名验证、时间同步和哈希；
- 权限、撤权、备份、恢复、暂停销毁和销毁证明；
- 目录状态变更及其直接证据。

### 12.2 抽样

- 所有已批准/已生效文件100%核验批准证据；
- 每类文件和记录、每种存储、每个密级至少抽一个；
- 全部覆盖修改、ID冲突、时间异常、恢复失败和销毁例外；
- 每个外来权威来源至少抽一个查新周期；
- 发现未授权修改时扩展至同账号、同时间窗和同对象族；
- 当前无真实档案总体，不报告档案运行合规率。
