# 证据包产品规范

## 1. 文件目的

本规范定义区块链电子数据研究和未来获准业务中的证据包边界、目录、完整性校验、披露、移交及验收要求。证据包的目标是让第二人员能够识别来源、重算关键事实、发现缺口，而不是以压缩文件、哈希值或界面截图替代对证据能力的证明。

当前版本只允许公开数据或经书面批准的模拟数据演练：

- 不代表司法鉴定意见；
- 不代表方法、工具、人员已获生产授权；
- 不允许将真实案件原始数据、个人信息或密钥提交到Git；
- `manifest`校验通过只证明登记对象与当前文件一致，不证明来源真实、采集合法、方法有效或结论正确。

## 2. 适用范围

### 2.1 纳入

- 公开链区块、交易、回执、日志和对应采集记录；
- 经合法授权取得的链下电子数据及其工作副本；
- 标准化事实、派生结果、分析记录、复核记录和交付物；
- 方法验证、工具验证、公开真值和端到端模拟案例；
- 完整包、最小披露包及其传输回执。

### 2.2 排除

- 钱包私钥、助记词、身份凭证、访问令牌和生产密钥；
- 未经授权取得的账户、设备、平台或个人数据；
- 资产控制、兑换、托管、定价或处置记录，除非另有合规批准的独立制度；
- 以Git提交时间替代可信时间、封存或司法保管链；
- 以供应商导出包、区块浏览器页面或单一RPC响应作为唯一事实来源。

## 3. 产品状态与包类型

|包类型|标识|内容范围|允许场景|当前状态|
|---|---|---|---|---|
|公开验证包|`public-validation`|公开原始对象、运行记录、结果、manifest和哈希|研究、同行复核|已形成样例，未获批准|
|内部研发包|`internal-rnd`|授权的模拟对象、验证底稿、缺陷和复核|内部研发|待演练|
|最小披露包|`minimum-disclosure`|仅包含回答明确问题所需对象和验证材料|经批准的外部沟通|未实现|
|完整受控包|`full-controlled`|案件范围内全部受控对象、血缘、保管和交付记录|未来获准业务|未实现|

公开样例及其状态见[`验证证据登记册`](../10-reference/10-validation-evidence-register.md)。实际对象保存在`validation-evidence/public/`，样例用于检验格式和复算路径，不能证明生产能力。

## 4. 角色与职责

|角色|主要职责|不得单独完成|
|---|---|---|
|案件/项目负责人|批准包目的、范围、披露级别和接收方|自行批准超授权披露|
|采集人员|登记来源、时间、工具、参数和原始对象|删除失败采集或覆盖原件|
|分析人员|建立派生血缘、方法引用和结果边界|把假设写成原始事实|
|独立复核人|恢复包、重算哈希与P0事实、记录差异|直接复制分析人员结果|
|质量负责人|检查格式、记录、缺陷和发布门|豁免未解释的P0差异|
|保管人员|封存、访问、复制、移交、回执和留存|兼任全部分析与批准角色|
|批准人|决定是否发布并接受残余风险|批准无授权或无复核的包|

人员不足无法职责分离时，包状态保持`draft`或`blocked`。

## 5. 详细控制要求

|控制ID|控制主题|强制要求|失败或阻断条件|
|---|---|---|---|
|PRD-005-C001|案件清单|根目录必须有`case-manifest`，记录包ID、去标识案件ID、目的、范围、授权引用、分类、创建人、创建时间和状态|缺授权引用、用途或分类|
|PRD-005-C002|证据对象清单|每个对象必须有唯一ID、类型、相对路径、字节数、SHA-256、来源ID和父对象ID|对象未登记、重复ID或路径越界|
|PRD-005-C003|原始数据目录|`raw/`对象只读保存；任何解析、重命名或换行转换均产生新对象，不覆盖原始对象|原始对象被改写或只保存截图|
|PRD-005-C004|标准化数据目录|`normalized/`仅保存字段映射后的事实，记录规则、版本、单位、时区和缺失值原因|默认值掩盖未知或无法回溯原始字段|
|PRD-005-C005|派生结果目录|`derived/`保存计算、图、表和中间结果；每个结果列出全部父对象、方法、工具及参数|存在无父对象的派生结论|
|PRD-005-C006|工具与环境清单|记录工具ID、版本、获取位置或哈希、运行环境、节点/数据源及关键配置|仅写产品名或在线服务名称|
|PRD-005-C007|方法版本清单|列出方法ID、冻结版本、适用范围、状态及偏离；未授权方法不得标为生产方法|引用不存在、暂停或范围不符的方法|
|PRD-005-C008|操作日志|日志按时间记录操作人、动作、对象、输入、输出、异常和决定；失败记录不得删除|关键步骤无日志或日志与对象时间冲突|
|PRD-005-C009|录像索引|仅在要求录像的活动中提供片段ID、文件ID、起止时间、哈希和对应步骤；不强制用录像替代结构化记录|应录像但无文件、索引或缺口说明|
|PRD-005-C010|复核记录|记录复核人、独立性、抽样、重算项、差异、结论和时间；P0差异全部关闭后才能发布|复核人与执行人为同一人或P0差异未关闭|
|PRD-005-C011|报告与附件|报告中的每项关键事实引用对象ID、字段/字节位置或计算记录；附件与正文版本一致|存在无法定位到证据对象的关键事实|
|PRD-005-C012|包根哈希|当前V1根哈希为按POSIX相对路径排序后拼接`sha256␠␠size_bytes␠␠path`行并计算SHA-256；必须记录算法ID|把V1根哈希称为Merkle根或算法未声明|
|PRD-005-C013|数字签名|只有签名算法、证书/公钥标识、签名范围、验证结果和密钥管理均完成验证后才可标记`signed`|仅有姓名图片、空签名字段或未验证签名|
|PRD-005-C014|加密封装|敏感包必须使用获批算法和密钥交付通道；加密前后对象、容器哈希和解密演练均登记|密码与包同通道、无法解密或无密钥接收确认|
|PRD-005-C015|最小披露包|由完整包生成，使用允许清单选择对象，保留来源包ID、删减理由、替代标识和重新计算的清单哈希|直接手工复制且无法证明删减边界|
|PRD-005-C016|完整包|完整包覆盖授权范围内全部原始对象、派生对象、日志、复核、缺陷、报告和保管事件|选择性遗漏失败记录或反向证据|
|PRD-005-C017|验证脚本|提供只读验证入口，至少检查Schema、路径、对象数、字节数、对象哈希、父对象引用和根哈希|脚本会修改对象或只输出笼统“成功”|
|PRD-005-C018|格式版本|`schema_version`使用语义化版本；破坏性字段变化提升主版本并提供迁移/冻结策略|无版本或旧读取器静默误读|
|PRD-005-C019|兼容性声明|列出验证过的操作系统、读取器、字符编码、压缩/加密格式和已知限制|把“理论可读”写成“已验证兼容”|
|PRD-005-C020|传输回执|移交双方核对包ID、容器哈希、对象数、时间、渠道、异常和接收决定；回执进入保管事件链|无接收确认、哈希不一致仍视为完成|

上述控制目前均为`not_implemented`；公开样例只构成局部设计证据。

## 6. 目录与清单规范

### 6.1 规范目录

```text
<package_id>/
  README.md
  manifest.json
  hashes.sha256
  case/
  authorization/
  raw/
  normalized/
  derived/
  methods/
  tools/
  logs/
  review/
  reports/
  custody/
  delivery/
```

空目录不得为了“看起来完整”而创建；缺失的条件性目录由`manifest`中的`omissions`说明。

### 6.2 必填包级字段

|字段|要求|
|---|---|
|`schema_version`|格式版本，不等于文档版本|
|`package_id`|稳定、不可复用且不含姓名/证件号|
|`case_id`|去标识引用；公开包使用模拟或公开项目ID|
|`package_type`|四类包之一|
|`purpose`|明确要支持的任务，不使用“全面分析”|
|`authorization_refs`|至少一项批准记录；纯公开研究注明公开来源边界|
|`created_at`|RFC 3339时间，包含时区|
|`created_by`|受控人员ID，不使用自由文本姓名作为唯一标识|
|`classification`|`public`、`internal`、`sensitive-case`或`restricted`|
|`status`|见6.4|
|`objects`|对象清单|
|`root_hash`|按声明算法计算|
|`root_hash_algorithm`|当前值为`sha256-sorted-path-lines-v1`|

仓库现有[`evidence-manifest.schema.json`](../schemas/evidence-manifest.schema.json)是V3草案，仅覆盖公开验证包所需的部分字段。它尚未实现本规范全部要求，使用者不得由Schema通过推导完整包合格。

### 6.3 路径与对象规则

- 路径使用相对路径和正斜杠；
- 禁止绝对路径、`..`、设备名、软链接逃逸和大小写冲突；
- `manifest.json`自身不列入`objects`，避免自引用；
- `hashes.sha256`是否列入对象必须由版本固定，不能在验证时临时选择；
- 同一字节对象可以被多个逻辑对象引用，但每个逻辑对象关系必须明确；
- 大对象分片时登记原容器、分片次序、每片哈希及重组哈希；
- 任何文件名不得包含自然人姓名、证件号码、账户口令或私钥材料。

### 6.4 状态机

```text
draft -> assembled -> verified -> reviewed -> approved_for_delivery -> delivered
   \         \          \          \                 \
    blocked   blocked    blocked    blocked           withdrawn
```

- `verified`仅表示机器校验通过；
- `reviewed`表示独立复核完成；
- `approved_for_delivery`必须有具名批准；
- `delivered`必须有接收回执；
- 内容变化后生成新包版本，不在已交付包上原位修改；
- 缺授权、哈希不符、父对象断裂或P0差异时进入`blocked`。

## 7. 完整性、签名与加密

### 7.1 对象哈希

V1使用SHA-256计算对象字节流。计算前不得做编码、换行、压缩或元数据规范化。若文件发生任何转换，转换结果作为新对象并引用父对象。

### 7.2 包根哈希

当前公开证据包采用：

1. 读取`objects`；
2. 按对象的POSIX相对路径升序排序；
3. 每行编码为`<sha256>  <size_bytes>  <path>\n`，字段间为两个ASCII空格；
4. 按UTF-8拼接；
5. 对拼接字节计算SHA-256。

该算法没有叶节点域分离、内部节点或包含证明，因此不是Merkle树。未来引入Merkle结构时必须使用新的算法ID、测试向量和迁移决策，不得复用V1名称。

### 7.3 数字签名

数字签名是后续能力，不是当前基线。签名至少覆盖不可歧义的manifest规范化字节、根哈希算法和包状态；验签必须在独立环境执行。密钥保管、撤销、证书链和长期验证未完成前，签名字段保持空或明确`not_implemented`。

### 7.4 加密封装

加密只保护机密性，不证明内容真实性或采集合法性。敏感包在独立受控存储中封装，Git只保存脱敏登记、哈希和批准后的公开材料。

## 8. 组装、验证与交付流程

1. 负责人冻结目的、授权、包类型和披露对象。
2. 采集人员登记原始对象，立即计算哈希并创建只读工作副本。
3. 分析人员逐项登记标准化和派生对象的父关系、方法、工具与参数。
4. 组装人员生成manifest、对象哈希清单和包根哈希。
5. 只读验证器执行Schema、路径、数量、大小、哈希、引用和根哈希检查。
6. 独立复核人从空目录恢复包，重算全部P0对象和抽样P1/P2对象。
7. 质量负责人核对授权、遗漏、缺陷、报告引用和状态。
8. 批准人决定阻断、内部留存或批准交付。
9. 保管人员按批准渠道交付，双方核对容器哈希并生成回执。
10. 交付后任何更正生成新版本并关联原包，不覆盖历史包。

## 9. 披露与数据最小化

最小披露不是“删到越少越好”，而是对明确问题提供充分且必要的对象。生成前必须形成：

- 接收方、用途和法律/合同依据；
- 包含对象允许清单；
- 被排除对象类别及理由；
- 去标识、遮盖或聚合规则；
- 对复算能力的影响；
- 来源完整包ID和生成记录；
- 独立复核与批准。

若删减导致关键事实无法复算，应增加必要对象或在报告中明确“无法独立复算”，不得仍宣称完整可验证。

## 10. 异常、拒绝与更正

|异常|立即动作|允许结果|
|---|---|---|
|对象哈希不符|隔离包、停止分析、保留差异副本|`blocked`|
|清单对象缺失|确认是否传输缺失或原始未取得|补采需新会话；否则无法判断|
|父对象断裂|停止发布派生结论|补建血缘并复核|
|授权范围不明|停止采集、分析和披露|等待书面澄清|
|敏感信息进入公开包|撤回公开版本、记录事件、评估通知|新建脱敏版本|
|签名无法验证|不得标记`signed`或`approved`|按未签名包处理|
|交付哈希不一致|双方保留记录并停止接收|重新传输或调查|
|已交付报告错误|冻结受影响包、启动影响分析|更正、撤回或补充|

## 11. 记录与留存

每个包至少保留：

- 组装请求和范围批准；
- 授权引用及披露决定；
- manifest、对象哈希清单和根哈希输入；
- 验证器版本、命令/参数、标准输出和退出状态；
- 独立恢复、抽样与差异记录；
- 缺陷、偏离、批准和残余风险；
- 传输容器哈希、接收回执和更正记录；
- 留存、法律保全、迁移与销毁事件。

留存期限必须由案件、合同、法律保全和内部制度共同决定；本规范不设置一个适用于所有数据的固定期限。

## 12. 用户故事与验收示例

### 12.1 第二复核人恢复公开验证包

**故事**：作为未参与采集的复核人，我需要只依赖包内说明重算对象和关键事实，以确认结果不是对执行人输出的重复抄录。

**给定**：一个`public-validation`包、空工作目录和已登记读取环境。

**当**：复核人运行只读验证、随机打开原始对象、重算P0字段及根哈希。

**则**：

- [ ] 所有对象路径均在包内；
- [ ] 对象数、字节数和SHA-256与manifest一致；
- [ ] 每个派生对象都能追溯到父对象、方法和工具；
- [ ] 包根哈希按`sha256-sorted-path-lines-v1`复算一致；
- [ ] 结果记录执行人、时间、环境、命令和实际输出；
- [ ] 任一P0差异使包保持`blocked`。

### 12.2 由完整包生成最小披露包

**故事**：作为交付负责人，我需要回答一个已授权的交易事实问题，同时不披露无关主体信息。

**验收**：

- [ ] 允许清单和删减理由在生成前获批；
- [ ] 新包保留来源完整包ID，但不暴露受限对象内容；
- [ ] 去标识处理生成派生对象且保留转换记录；
- [ ] 新manifest和根哈希独立计算；
- [ ] 报告只引用披露包内可访问对象；
- [ ] 复核人确认删减未改变回答边界。

### 12.3 接收方发现容器哈希不一致

**故事**：作为接收方，我需要在文件损坏或包被替换时拒绝接收。

**验收**：

- [ ] 回执记录发送方和接收方计算值；
- [ ] 状态不进入`delivered`；
- [ ] 原传输文件被隔离且不覆盖；
- [ ] 重传形成新传输事件；
- [ ] 调查结论区分传输损坏、错误版本和内容变更。

## 13. 验收门与测试映射

|门|最低证据|失败结果|
|---|---|---|
|G1范围|目的、授权、分类、包类型|不允许组装|
|G2对象|对象清单、路径、哈希、父关系|`blocked`|
|G3机器验证|具体测试输入、步骤、实际输出|不得称`verified`|
|G4独立复核|从空目录恢复、P0全量复算|不得称`reviewed`|
|G5批准|具名批准、残余风险、披露清单|不得交付|
|G6接收|容器哈希和双方回执|不得称`delivered`|

本规范的20项测试见`catalogs/tests.csv`。在首个端到端模拟包完成前，状态保持`not_executed`。
