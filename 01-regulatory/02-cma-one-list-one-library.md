# CMA一单一库能力决策与申报准备

## 1. 文件目的

将2026年6月1日起实施的“一单一库”制度转化为能力项目查询、对象/项目/参数/标准表述、库外项目处置和CMA标志使用控制。

本文件是生产体系中的单一权威来源。与旧版本、会议纪要、原型界面或口头约定不一致时，除非存在经批准的变更单，否则以本文件及其引用的受控记录为准。

## 2. 适用范围

### 2.1 纳入范围

- CMA一单一库能力决策与申报准备涉及的研发、验证、运行和质量活动
- 对外技术服务前的内部评审与批准
- 相关人员、工具、数据、场所和供应商的受控管理

### 2.2 明确排除

- 替代司法行政、市场监管、法院、检察机关或公安机关的法定判断
- 未经授权的数据获取、身份调查、交易撮合或资产处置
- 将概率性分析包装为自然人身份、违法属性或法律责任的确定结论

## 3. 角色与职责

- **文件责任人（合规负责人）**：维护本文件的准确性、可执行性和变更记录。
- **批准人（质量负责人）**：确认范围、风险、资源和对外承诺边界。
- **质量负责人**：验证本文件是否与质量手册、记录控制和审计要求一致。
- **执行人员**：仅在授权范围内操作，发现前提不成立时立即停止并升级。
- **独立复核人员**：不得直接复制执行人员的结论，应重新核对证据链和关键计算。

## 4. 核心原则

1. 原始证据不可覆盖；修订、派生和展示对象必须保持独立身份。
2. 链上技术事实、规则推断、统计推断、主体归属意见和法律判断分层表达。
3. 第三方RPC、区块浏览器和商业标签库只能作为辅助来源，不能成为关键事实的唯一依据。
4. AI或Agent只能执行受控检索、候选生成和一致性检查，不得独立批准最终结论。
5. 任何结果都必须能够指向输入、工具版本、参数、环境、执行人、复核人和适用方法。
6. 证据不足、来源冲突或方法越界时，系统应输出事实缺口、候选集合或无法判断。

## 5. 详细控制要求

### REG-002-C001｜事项清单查询

- **控制目的**：在CMA一单一库能力决策与申报准备中，使“事项清单查询”形成可验证、可追溯、可复核并可在失败时安全停止的生产能力。
- **强制要求**：“事项清单查询”应被拆分为可验证步骤；每一步都要指定责任角色、前置条件、执行记录、异常分支和完成定义。
- **输入条件**：“事项清单查询”的输入至少包含原始对象或正式记录、采集时间、数据源等级、当前版本以及前序环节的通过证据。
- **执行记录**：“事项清单查询”不得只保存最终截图；应同时保存机器可读结果、过滤条件、排序规则、失败尝试和人工复核批注。
- **验收证据**：以受控记录与哈希清单证明“事项清单查询”已经执行；仅有会议纪要、口头确认或界面截图不构成充分证据。
- **阻断条件**：出现“来源、授权或对象身份无法确认”，或“事项清单查询”的关键输入无法回溯时，停止强结论并创建异常记录。
- **责任角色**：合规负责人负责“事项清单查询”的执行或管理；质量负责人核对关闭证据，批准人处理超出既定风险容忍度的事项。

### REG-002-C002｜能力项目库查询

- **控制目的**：在CMA一单一库能力决策与申报准备中，使“能力项目库查询”形成可验证、可追溯、可复核并可在失败时安全停止的生产能力。
- **强制要求**：对“能力项目库查询”的判断不得仅依赖界面展示或供应商结论，关键事实应能够回溯至原始对象、协议字段或受控记录。
- **输入条件**：进入“能力项目库查询”环节前，应确认案件状态允许、所需数据完整、依赖工具已批准且不存在未关闭的P1不符合。
- **执行记录**：完成“能力项目库查询”时，执行人应登记正常路径和异常路径，特别说明数据源切换、重试、舍入、排除和降级行为。
- **验收证据**：设计评审记录；证据必须直接显示“能力项目库查询”的输入、实际输出、复核差异和最终处置。
- **阻断条件**：如果关键字段在独立来源间冲突且无法解释，则“能力项目库查询”只能输出事实缺口或候选集合，不得自动降级数据源后继续。
- **责任角色**：质量负责人负责“能力项目库查询”的执行或管理；质量负责人核对关闭证据，批准人处理超出既定风险容忍度的事项。

### REG-002-C003｜审批决定时点

- **控制目的**：在CMA一单一库能力决策与申报准备中，使“审批决定时点”形成可验证、可追溯、可复核并可在失败时安全停止的生产能力。
- **强制要求**：实施“审批决定时点”时应优先保证可重现性和证据完整性，而不是追求最大覆盖率；无法满足前提时输出拒绝结论。
- **输入条件**：对于“审批决定时点”，执行人需先列出要验证的事实、允许使用的数据源和不能回答的问题，复核人确认后开始。
- **执行记录**：执行记录应逐步说明如何处理“审批决定时点”，保存实际命令、API参数、原始响应或表单字段，并记录每次人工选择的理由。
- **验收证据**：至少提交一份与“审批决定时点”对应的方法确认报告，并附正常、边界和失败样本的对象ID及哈希。
- **阻断条件**：当“审批决定时点”超出已验证方法范围、复核无法重现或工具版本、参数或运行环境未锁定时，必须阻断发布。
- **责任角色**：技术负责人负责“审批决定时点”的执行或管理；质量负责人核对关闭证据，批准人处理超出既定风险容忍度的事项。

- **验收证据**：验收包包含“标准现行性”的工具验证报告、独立重算结果、异常记录和适用范围声明。

- **责任角色**：方法负责人负责“标准现行性”的执行或管理；质量负责人核对关闭证据，批准人处理超出既定风险容忍度的事项。

## 12. 监管结论分级与决策矩阵

|等级|含义|允许用途|禁止用途|
|---|---|---|---|
|A：明确官方规则|来源为现行法律、规章、正式公告或办事指南，适用性已复核|形成内部强制控制、申请材料和合同边界|不得扩大到文件未覆盖的项目或地区|
|B：官方解释或公开答复|来源权威但可能具有场景或时间限制|用于形成待验证实施方案|不得代替行政许可决定或个案裁判|
|C：内部法律与技术解释|团队基于A/B级来源作出的分析|用于研发、差距评估和问题准备|不得对外宣称主管机关已认可|
|D：待确认事项|来源不足、不同机关口径可能不同或涉及新兴能力|进入主管机关问题包并设置阻断条件|不得进入强结论、宣传或正式能力范围|

### 决策规则

1. 能力范围、申请顺序、人员资格和报告标志等事项出现D级问题时，项目不得自行推定通过。
2. 同一事项存在冲突来源时，保留全部来源、发布日期和适用范围，并提交更高权威来源或书面确认。
3. 正式申报材料冻结前，对全部A/B级来源重新查新；网页快照和下载文件必须登记哈希。
